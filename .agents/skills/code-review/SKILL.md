# コードレビュー（オーケストレータ）

mainブランチ（既定）からのローカル差分を対象に、バックエンド/フロントエンドどちらに該当するかだけを判定し、観点ごとの実行要否判定と並列レビューは各サブスキルへ委譲する。サブスキルから返された検証済みの指摘とセキュリティの指摘を統合して報告する。

このスキル自身はリファレンスも観点別の実行条件判定も持たない。観点定義と実行条件判定は `code-review-backend` / `code-review-frontend` の2サブスキルが持つ。この2つは本スキルからのみ呼び出される内部サブスキルであり、単体では起動しない。

## ワークフロー

### 1. ベースブランチの決定と差分取得

ベースブランチは既定で `main`。ユーザーから別ブランチの指定があればそちらを使う。

```bash
BASE_BRANCH=main  # ユーザー指定があれば上書き
git fetch origin "$BASE_BRANCH"
git diff "origin/$BASE_BRANCH"...HEAD
git log "origin/$BASE_BRANCH"..HEAD --oneline
git diff "origin/$BASE_BRANCH"...HEAD --name-only
```

`git fetch` でベースブランチを最新化してから、リモート追跡ブランチ（`origin/$BASE_BRANCH`）を基準に差分を取る。ローカルの `$BASE_BRANCH` ブランチ自体は切り替えず、更新もしない。

変更がない場合はその旨を伝えて終了する。

### 2. 対象領域の判定

変更ファイル一覧から、起動するサブスキルを決める。観点ごとの実行条件（モデル/スキーマの変更有無・テストの有無等）はサブスキル自身が判定するため、ここではバックエンド/フロントエンドどちらに該当するかのみを判定する。

| 領域 | 判定条件 | 起動するサブスキル |
|---|---|---|
| バックエンド | `*.rb`・`Gemfile` の変更 | `code-review-backend` |
| フロントエンド | `*.ts`・`*.tsx`・`*.js`・`*.jsx`・`package.json` の変更 | `code-review-frontend` |

どちらの領域にも該当しない場合はその旨を伝えて終了する。

### 3. サブスキルの起動

該当するサブスキルを Skill ツールで起動し、手順1で確定した diff range（`origin/$BASE_BRANCH...HEAD`）を渡す。サブスキルはこれを使って自分で対象領域の判定・観点ごとの並列レビュー・検証パスまでを行い、検証済みの指摘一覧（個々の指摘ブロックのみ）を返す。

バックエンド・フロントエンド両方に該当する場合は、2つのサブスキルを並列で起動する。

### 4. セキュリティ観点の構成（オーケストレータが直接実行）

1. Skillツールで `security-review` スキル（ビルトイン）を起動し、手順1で確定した差分全体（バックエンド・フロントエンドを問わない）を対象にレビューさせる。結果は次の形式にマッピングする: 観点 / 重大度（🔴Critical・⚠️Warning・💡Suggestionのいずれか）/ 信頼度（0〜100。0:誤検知 / 25:やや自信あり / 50:中程度の自信 / 75:高い自信 / 100:確実）/ ファイル:行 / コード引用 / 問題の説明 / 修正案
2. `security-review` が利用できない場合、代替のリファレンスは持たない。バックエンド対象があれば、**セキュリティ観点を省略して続行するか、レビュー自体を中断するかをユーザーに確認する**

### 5. 結果の統合と出力

各サブスキルから返された検証済みの指摘と、手順4のセキュリティの指摘を統合する。security-review の指摘についても、サブスキルの指摘と同様に以下の検証パスを適用する（サブスキルの指摘は各サブスキルで検証済みのため再検証しない）。

- 引用されたコードが実際にdiffの変更行に存在するか確認する。存在しない・変更行でない指摘は破棄
- 指摘内容が引用コードと整合しているか確認する。誤読・文脈の見落としがあれば破棄または信頼度を下げる
- 信頼度スコアが75未満の指摘はここでフィルタリングする
- 同一箇所への重複指摘は最も適切な観点に統合する。ただし統合してよいのは**同じ問題**を指す指摘のみ（バックエンドとフロントエンドは対象ファイルが分かれるため通常は発生しないが、セキュリティ観点との重複は起こりうる）

以下は誤検知として除外する:

- 変更前から存在していた問題（ただし「変更したロジックへのテスト欠落」は、テスト基盤が元から無い場合でも新規の問題として扱い、除外しない）
- リンター・型チェッカー・コンパイラが検出する問題
- CLAUDE.md / AGENTS.md で明示的に抑制されている問題（lint ignoreコメント等）
- 意図的な機能変更に対する指摘
- 変更していない行に対する指摘
- シニアエンジニアが指摘しないような些細なnitpick

統合後、重大度（Critical → Warning → Suggestion）、同一重大度内は信頼度の降順でソートする。**形式は以下のテンプレートに厳密に従い、日本語で出力する**（サブスキル・サブエージェントの出力言語に引きずられない）。

指摘がある場合:

````markdown
## コードレビュー結果

N件の指摘:

### 1. 🔴 [観点] 指摘の要約

**ファイル**: `path/to/file.rb:42`
**信頼度**: 85/100
**該当コード**:
```ruby
def complete!
  self.completed_by = Current.user
end
```
**詳細**: 具体的な問題の説明と改善案

### 2. ⚠️ ...
````

指摘がない場合:

```markdown
## コードレビュー結果

指摘なし。実行した観点: [実行した観点の一覧]
```

いずれの場合も、末尾に「実行した観点」と「スキップした観点（実行条件を満たさなかったもの）」を1行ずつで明記する。各サブスキルが自分で判定した観点も含める（サブスキルからの返答に含めさせる）。
