# コードコメント規約

## 規約1. 原則コメントは不要

コメントの役割は、**設計者の頭の中にあったが、コードでは表現しきれなかった情報を記録すること**である。コードが表現できるのは実装（どう動くか）だけで、意図（なぜそうしたか）と暗黙の依存はコードに現れない。この失われた情報は不明瞭さとなり複雑性の主要因になる。

ただし、コードで表現できない情報の受け皿はコメントだけではない。

| 表現したいもの | 手段 |
|---|---|
| 振る舞いの仕様 | クラス名・メソッド名・テストケースの記述 |
| 変更理由の Why | コミットメッセージのボディ・PR説明 |

**これらで表現できるものをコメントに書くのは重複**であり、更新されずに腐る。コメントは他のどの手段でも表現できない情報だけを引き受ける。
だから既定は「書かない」であり、書く側に正当化の責任がある。迷ったら書かない。

判定基準: コードから自明なことは書かない。そのコメントを消して、コードとテストだけでレビュアーが理解できるなら不要


## 規約2. 書くのは「設計判断の根拠」「非自明な制約」のいずれかに該当する場合のみ

この2カテゴリのどちらかに該当することを正当化できる場合に限り、規約1より優先してコメントに書く。

### 設計判断の根拠

複数の選択肢から自明でないトレードオフで選んだ理由。コードから読み取れない「なぜ他の方法にしなかったか」。

```ruby
# 退会ユーザー除外はサブクエリ（user: User.active）で行う。joins(:user)にしないのは、
# 他のscopeが独自にusersをJOINしており、JOINが衝突するため。
```

マジックナンバー・定数も、その値を選んだ根拠が非自明ならここに該当する。根拠の分からない定数は将来の変更で事故を起こす。

```javascript
// リトライ上限。外部APIのレート制限が 3req/sec のため
const MAX_RETRY = 3;
```

### 非自明な制約

呼び出し順序・状態・事前条件・副作用・例外など、名前から推測できない暗黙の依存。

```ruby
# mutex.lock より先に呼ぶこと。逆順だとデッドロックする (issue #482)。
```

名前や型で表現しきれない精密な情報——単位、境界値の含む/含まない、nil が意味すること、不変条件、非自明な計算量——もここに含む。

```ruby
# 単位はミリ秒。0 はタイムアウト無効を意味する
attr_reader :timeout
```

## 規約3. コードの言い換え・仕様の説明はコメントで書かない

### コードの言い換え

コードを自然言語で繰り返すコメントは記述しない。命名やリファクタリングで解決すること。

```ruby
# 不可
user = get_user(id)  # ユーザーを取得する

# 可
user = get_user(id)
```

```
# 不可（見れば分かる）
i += 1  # i に 1 を足す

# 可（規約2「非自明な制約」に該当する意図）
i += 1  # ヘッダ行をスキップするため先頭をずらす
```

### 仕様・ビジネスルールの説明

コードが実現する仕様をコメントで説明しない。「Whyを述べているから良いコメント」ではない——実装の選択理由（トレードオフ）以外の Why はコメントに書かない。仕様はクラス名・メソッド名・テストが語る。

```ruby
# 不可（仕様のナレーション。メソッド名とテストで表現できる）
# 退会コーチのプランは一覧に出さない
scope :listable, -> { joins(:coach).merge(Coach.active) }

# 不可（メソッドの動作説明 + 仕様の言い換え）
# 退会済みユーザーのプロフィールは直リンクでも参照不可（find_by!でRecordNotFoundを発生させる）
user = User.active.find_by!(id: id)

# 可（コメントなし。仕様はテストケースとして記述する）
user = User.active.find_by!(id: id)
```

## 規約4. ワークアラウンドには理由と出典へのリンクを書く

バグ回避や非直感的な実装には、そうせざるを得なかった理由と、出典へのリンクを必ず添える。後任が「なぜこんな書き方なのか」を追える状態にするため。リンク先は Issue・PR・仕様書・外部のバグ報告のいずれか。

```ruby
# Ruby 3.2 の Timeout.timeout がスレッド内で発火しない問題の回避 (https://bugs.ruby-lang.org/issues/xxxxx)
```

理由だけあってリンクが無いものも違反。出典が無いと、回避対象が解消されたときにワークアラウンドを畳めない。

## 規約5. ドキュメンテーションコメントは言語標準の形式に従う

Python: docstring／JS・TS: JSDoc・TSDoc／Java: Javadoc／Go: doc comment／Ruby: RDoc・YARD 等。

形式に従うことと、書く必要があることは別。ドキュメンテーションコメントも規約1〜3の判定を受ける。

## 規約6. コメントは日本語・体言止めで書く

文体は体言止め。ドキュメンテーションコメント・インラインコメントとも同じ。

## 規約7. コードとコメントの同期

**古いコメントは、コメントが無いことよりも有害。** 変更によってシグネチャや挙動が変わったのに、隣のコメントが古い記述のまま取り残されていないか。残せないなら削除も正解。
