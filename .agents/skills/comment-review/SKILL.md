# コメント規約レビュー

コードコメントが規約に従っているかをレビューし、違反をフィードバックする。**修正そのものは行わず、何がどう違反しているかと直し方を返す**のが本スキルの責務である（PostToolUse 起点なら、それを受け取った本体エージェントが自分で直す）。

## 規約の読み込み

レビューを始める前に、本スキルのディレクトリ配下の `references/comment-conventions.md` を必ず Read する。これが規約の正本であり、判定はすべてここに書かれた規約1〜7に基づいて行う。**本スキルは規約を再掲しない**（二重管理は規約の分岐を生むため）。

`~/.claude/rules/development-principles.md`（Codex では `~/.codex/AGENTS.md`）の「コードコメント規約」は同じ規約の要約であり、正本と食い違って見える場合は正本が優先する。

レビューの軸は「余分な What を削らせる」と「規約2に該当するのに欠けている情報を補わせる」の両輪になる。規約は default-deny であり、**判断が付かないコメントは削除側に倒す**。

## レビュー対象の特定

**変更部分のコメントだけを見る。** 無関係な既存コメントを巻き込んで指摘すると、本来のレビュー目的（いま入った変更の品質を守る）がぼやけ、ノイズになる。

- **フック起点**（Claude Code の PostToolUse 等の自動リマインダーから「いま編集したコメントを見直せ」と促された場合）: 直前に編集・作成したファイルの**追加・変更したコメント**が対象。必要なら `git diff` で変更箇所を確認する。
- **手動起動**（ユーザーが「コメントレビューして」等）: 既定では `git diff main...HEAD` の変更部分。ユーザーがファイルや範囲を指定した場合はそれに従う。

変更行に隣接していて、**変更によって陳腐化した既存コメント**は対象に含める（規約7）。それ以外の既存コメントには触れない。

## 照合の進め方

変更部分の各コメントを、正本の規約と順に照合する。

1. **規約3に該当するコメントを削除対象にする** — コードの言い換え、仕様・ビジネスルールの説明
2. **残ったコメントが規約2に該当するか検証する** — 該当を正当化できないものは規約1（原則不要）により削除対象
3. **残すコメントを規約4〜7で検査する** — ワークアラウンドの出典リンク、doc形式、日本語・体言止め、変更による陳腐化
4. **規約2・4に該当するのに欠けている情報を探す** — 非自明なトレードオフ・根拠のない定数・出典のないワークアラウンド・名前から推測できない呼び出し順序や単位

「コメントが在るべきなのに無い箇所」は 4 で拾う。ただし過剰要求は後述の誤検知に当たる。

## フィードバックの作り方

修正は本体エージェントの仕事。本スキルは**何が問題で、どう直すべきか**を渡す。違反ごとに次を示す:

```
- `path/to/file.rb:42` [規約N] 何が問題か。→ どう直すべきか。
```

直し方は、**正解が一意に決まるかどうか**で書き分ける:

- **削除・整形（正解が一意）**: 具体的な修正後の文言や「この行のコメントは削除」と明示する。例: 自明なWhatコメント、体言止め違反、doc形式違反。
- **Why・根拠の欠落（正解が一意でない）**: 中身を**こちらで書かない**。「なぜこの値/順序/方法を選んだかを記す」と**指示する**にとどめる。

  これは重要で、レビュアが意図を憶測で埋めると、それ自体が「コードと不一致な古いコメント」（規約7違反）の種になる。ただし PostToolUse 起点で**そのコードを書いた本体エージェント自身**が直す場合、本体は意図を知っているので正確に補える。だからこの場合の指示は「お前はなぜそう書いたか知っているはずだ。それをコメントに残せ」という促しになる。

違反が無ければ、その旨を簡潔に伝えて終わる。無理に指摘を捻り出さない。

## 誤検知を出さないために

ノイズの多いレビューは無視されるようになる。次は**指摘しない**:

- コードを読めば分かる程度のことに、過剰に Why コメントを要求する（短く自明なローカル変数・ゲッター等まで説明を求めない）
- 名前・テスト・コミットメッセージで表現すべきものをコメントで補うよう要求する（規約3違反を誘発する。補うべきは規約2の2カテゴリだけ）
- 変更していない行・無関係な既存コメント
- リンタ・フォーマッタ・型チェッカが機械的に直す範囲（インデント等のスタイル）
- 意図的な仕様変更そのものへの異議（コメントの良し悪しがスコープであって、実装の是非ではない）

「このコメントが無い／余計なことで、半年後の自分や他人が困るか」を判断基準にする。困らないなら指摘しない。
