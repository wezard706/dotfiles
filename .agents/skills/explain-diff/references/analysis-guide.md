# 変更の解析方針

レポートに何を書くかは `assets/report-shell.html` の章コメントが定める。ここでは、そこへ書く材料をどう集めるかを扱う。

## 変更意図へのグループ化

グループの単位は、ファイルでもディレクトリでもなく、**1つの変更意図を完結させる範囲**にする。レビュワーは「なぜこの変更が必要だったか」を1タブで読み切れる状態を期待している。

- renameと、その呼び出し元・import・対応テストは同じグループにする
- 1ファイル内に異なる変更意図があれば、hunk単位で別グループへ分ける
- 生成コード・スナップショット・ロックファイルは、それを生んだ変更と同じグループにする
- 意図を特定できない変更を、説明のつくグループへ紛れ込ませない。独立させて「意図を特定できなかった」と書く

グループの数が10を超えると、タブが読み切れなくなる。その場合はグループ化の粒度が細かすぎないか見直す。逆に、1グループに無関係な変更が同居していないかも確認する。

## ユーザー影響の判定

レビュワーはアプリケーションのUXを知らない前提で書く。影響の有無は、コードの見た目ではなく次の証拠から判断する。

1. 画面表示・i18nの追加削除
2. ルート・エンドポイントの増減、引数や返り値の変化
3. E2Eテスト・feature specの変化
4. 機能ドキュメントの変化

「利用者から見て変わらない」は、上のいずれも変化していないことを確認したときだけ主張する。確認していないだけの場合は、不明として残す。

上の材料が対象リポジトリに存在しないこともある。**材料が無いことは「変わらないと確認できた」ではない。** その場合は、公開インターフェースと戻り値が変わらないことを別の根拠で示せたときだけ確認済みとして扱う。示せないなら不明として残す。

間接的な影響（性能、整合性、権限の境界）も利用者影響に含める。ただし**観測できる差が出る条件を具体的に書けるものだけ**を含める。「この件数を超えると一覧の表示が遅くなる」「この操作の後に別の画面で古い値が見える」のように書けるなら利用者影響。書けないなら、利用者が違いを観測できる保証が無いということなので、この章には書かない。

## 業務フロー図の作り方

全体像と変更意図ごとのコード解説には、業務フロー図（シーケンス図）が必須。**作り方は `sequence-diagram` スキルの規則に従う。** エントリポイント探索・展開/停止ルール・ラベル規則をこのスキルへ複製しない。

抽象度は章で決まっているので、`sequence-diagram` スキルが抽象度を聞いてくる手順は飛ばし、こちらから指定する。

| 章 | 抽象度 | participant | 展開する範囲 |
|---|---|---|---|
| 変更の全体像 | 概念レベル | 利用者・APIサーバー・データベース等の役割名 | 業務の骨格だけ |
| 変更意図ごとのコード解説 | クラス単位 | その変更意図が触れるクラス名 | 触れる区間のみ。他は圧縮 |

`sequence-diagram` スキルは図を `./tmp/sequence_<slug>.md` へ保存するが、レポートへ載せるのは `sequenceDiagram` ブロックだけ。章断片HTMLへ `<pre class="mermaid">` として写す。

### E2Eを保つ

起点の participant は常に**利用者**にする。エントリポイントのクラスから始めない。レビュワーはアプリケーションを知らないので、コードの入口から描かれても自分の知っている操作と結び付けられない。

図が大きくなったら、区間を切り落とすのではなく**関係の薄い区間を1メッセージへまとめて圧縮する**。「利用者 → APIサーバー: 一覧を開く」の1本に畳めば、E2Eを保ったまま短くできる。

### 変更前の図をどう起こすか

`diff-snapshot.json` には変更後のコードと差分しか無い。変更前の図は基準ref側のコードから起こす。

```bash
git show <base-ref>:<path>
```

変更前後でフローが変わらないと判断したなら、図は変更後の1枚だけにして、変わらない旨を本文に書く。「変わらないので省いた」ことが読み手に伝わらないと、描き忘れと区別が付かない。

### 正常系のみ

`sequence-diagram` スキルの方針をそのまま継ぐ。例外・バリデーション失敗・業務上の中断分岐は描かない。ただし**その変更が異常系の扱いそのものを変えた場合**は、変わった分岐だけを描く。それが変更の主題である以上、省くと図が変更を説明しなくなる。

## 品質の判定は行わない

このスキルは変更を説明するのであって、良し悪しを判定しない。解析中に問題が見えても、レポートへ「ここは直すべき」とは書かない。

書けるのは、**レビュワーが自分で判断するための材料**まで。「この分岐は N 件を超えると全件走査になる」は事実なので書いてよいが、「非効率なので修正すべき」は判定なので書かない。境目は、書いた内容がコードから確認できる事実かどうかにある。

内部品質の指摘が必要な場合は `code-review` スキルが別途担当する。

## 大規模差分

先に全差分の一覧（`diff-snapshot.json` の `files`）から変更意図を洗い出し、グループ化を確定させてから、グループ単位で解析する。

- 差分そのものは省略できない。ビルダーが未割り当てのhunkを検出して失敗する
- 差分外コードの抜粋量は抑えてよい。理解に必要な範囲だけを `<details>` に入れる
- 解析し切れなかった範囲は、そのグループの説明に何が未解析かを明記する

## 生成物の確認

ビルド後、次を確認する。

- 標準出力の「省略した章」が意図通りか
- ブラウザで開き、図が描画されるか（Mermaidの記法誤りは図が出ないことで分かる）
- 変更意図タブがすべて表示され、各タブに差分があるか
- 行をクリックするとコメント欄が開くか

図が描画されない場合はMermaidの記法誤りを疑う。記法の落とし穴は [authoring-guide.md](authoring-guide.md) の「図」を参照する。
