# 開発原則

## 基本原則

- **変更容易性（ETC原則）**が最も重要です。将来の変更コストを常に意識して設計して下さい
- **戦略的プログラミング**: 短期的な成果よりも長期的な成果をもたらす理想的な設計を重要視して下さい
- **モデリング**: 良い設計は良いモデルから生まれます。実装を行う前に必ずモデリングを行って下さい。

## 命名原則

- 名前で「仕様を語る」ことを心掛けて下さい
- 「何（What/How）」より「なぜ（Why/Purpose）」を意識した名前にして下さい
- 技術用語よりもビジネス用語を使って下さい

## 重要なプログラミング原則

- 単一責任の原則を意識して下さい
- Tell, Don't Ask を意識して下さい
- 継承よりも集約を優先して下さい
- 高凝集・疎結合を意識して下さい
- 関数型プログラミングの純粋関数とイミュータブルを意識して下さい

## コードコメント規約

コメントは位置で2系統に分かれ、既定が逆になる。

### 宣言系（`class`・`module`・メソッド定義・`attr_*` に付くコメント）— 既定は「書く」

- `class`・`module`: 責務を述べる散文を書く
- public メソッド: 責務と契約の散文 + rbs-inline の `#:` 型注釈を書く
- private・protected メソッド: `#:` 型注釈を書く。散文は「設計判断の根拠」「非自明な制約」に該当する場合のみ
- `attr_*`: 行末に `#: Type` を書く
- 散文に書くのは、名前と型で表現しきれない事前条件・副作用・戻り値の意味・投げる例外。メソッド名の言い換えは不可
- `*_spec.rb` と `db/migrate/` は対象外

### 実装系（メソッド本体内など、宣言に付かないコメント）— 既定は「書かない」

- 原則コメントは不要
- 書くのは「設計判断の根拠」「非自明な制約」のいずれかに該当する場合のみ
- コードの言い換え・仕様の説明はコメントで書かない
- ワークアラウンドには理由と出典へのリンクを書く

### 両系統に適用

- コメントは日本語・体言止めで書く
- シグネチャや挙動が変わったら隣のコメントも直す。古いコメントはコメントが無いことより有害
